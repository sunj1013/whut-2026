防御性编程与高效调试

主讲：孙骏  |  李民
模块一：防御性编程与边界测试
痛点：用户的输入是不可预计的 你以为用户会乖乖输入 85，但他可能输入了 -5 或者 120。如果直接进入判断，程序可能会输出错误结果。
❌ 错误示范：毫无防备的成绩判断 
int score;
scanf("%d", &score);

// 如果用户输入 120，也会输出 A
if (score >= 90) {
    printf("A\n");
} else if (score >= 80) {
    printf("B\n");
} else {
    printf("C\n");
}
✅ 解决：输入合法性校验（第一道防线） 在做任何核心判断之前，先拦截异常数据。如果数据非法，直接处理掉，后面的代码连进都进不来。
案例 1：带防御的代码 
int score;
scanf("%d", &score);

// 第一步：先判断是否合法
if (score < 0 || score > 100) {
    printf("输入错误！成绩必须在0~100之间。\n");
} 
// 第二步：合法才进入正常判断
else if (score >= 90) {
    printf("A\n");
} else if (score >= 80) {
    printf("B\n");
} else {
    printf("C\n");
}
边界值测试：最容易漏分的地方 写完判断条件，脑子里一定要过一下：如果输入刚好等于分界线（如 60）会怎样？
案例 2：及格线的致命错误 
// 错误写法：输入 60 会被误判为不及格
if (score > 60) {   // 这里少了一个 =
    printf("及格\n");
} else {
    printf("不及格\n");
}

💡 口诀：写完条件，测两端（0 和 100）、测中间、测刚好压线的值。

模块二：Debug 调试技巧
痛点：为什么它总是不按套路出牌？ 写了复杂的 else-if 或者嵌套 if，输入一个数，结果什么都不输出，或者输出了莫名其妙的句子。光看代码找不到问题，只能靠猜。
技巧一：printf 大法（分治定位法） 在黑盒里放几个“探照灯”。在代码中间插入 printf，看程序到底执行到了哪一步，关键变量的值对不对。
案例 3：多分支的幽灵 Bug 
int score = 85; // 假设输入 85
scanf("%d", &score);

if (score >= 90) {
    printf("A\n");
} else if (score >= 80) {
    printf("探针 1：进入了 80 段\n"); // 探针
    if (score >= 85) {
        printf("探针 2：进入了 85 段\n"); // 探针
    } else {
        printf("B\n");
    }
}

💡 用法：如果屏幕上连“探针 1”都没打印，说明前面的条件写错了；如果打印了探针 1 但没打印 2，说明内层条件出了问题。

技巧二：IDE 调试三剑客 掌握调试工具（如 Code::Blocks、Dev-C++ 或 VS Code），比你想象的要强大得多。
  • 断点（Breakpoint）：在代码左侧行号旁边点一下，出现一个红点。程序运行到这里就会停下来，等待你的指令。
  • 单步执行（Step）：在 Code::Blocks 中按 F8（Dev-C++ 按 F10）。程序会一步一步往下走，你能清楚地看到它进入了哪个分支。
  • 观察变量（Watches）：在 Code::Blocks 中，点击菜单栏 Debug -> Debugging windows -> Watches。把你关心的变量（如 c）加进去，单步执行时，你会亲眼看到它的值是怎么变化的。
案例 4：用单步调试看清“悬空 else” 
int a = 2, b = -1, c = 2;
if (!a) {           // 在这里打断点
    if (b < 0) {
        c = 0;
    } else {
        c += 1;
    }
}
printf("%d", c);

💡 操作：按 F8 往下走，你会发现因为 a = 2，!a 为假，程序会直接跳过整个内部的大括号，根本不会去判断内层的 else。盯着 Watches 窗口里的 c，你会发现它的值始终是 2，根本没变过。
